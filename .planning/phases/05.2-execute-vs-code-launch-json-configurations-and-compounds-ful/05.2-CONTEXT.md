# Phase 05.2: Execute VS Code Launch.json Configurations and Compounds - Context

**Gathered:** 2026-05-05
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 05.2 turns dap-cli's existing lossy `.vscode/launch.json` support into agent-runnable F5 for real VS Code-style configurations and compounds. The phase should faithfully resolve a workspace launch file, apply variable substitution and platform overlays, pass adapter-native fields through to `js-debug` and `debugpy`, discover configurations and compounds, and execute a compound as a coordinated multi-session debug run.

The motivating target remains the `VS Code` compound in `/Users/roblou/code/vscode/.vscode/launch.json`: one renderer launch plus four process attaches under a shared compound group. The phase does not add new adapters, VS Code extension-command execution, interactive input variables, event streaming, a graphical UI, or a full VS Code task runner.

</domain>

<decisions>
## Implementation Decisions

### Compound Session Model
- **D-01:** Compounds should be first-class groups in dap-cli, not merely a naming convention over peer sessions. Downstream planning should persist enough compound metadata for agents to inspect the group and close it as one coordinated run.
- **D-02:** Compound shutdown should honor VS Code `stopAll`: if `stopAll` is true or omitted, closing one member closes the whole group; if false, peers may continue independently.
- **D-03:** Compound members should stay individually targetable through derived session names like `<compound>/<member>`, while exposing compound group metadata in session/status output.
- **D-04:** Compound startup should be failure-clean: if one member fails during startup, dap-cli should fail the compound launch and clean up any members already started, with diagnostics that explain which member failed.

### Launch.json Fidelity Boundary
- **D-05:** Adapter-native fields should pass through by default after resolution. Replace the current tight allowlist behavior with full passthrough plus a small known-bad denylist where needed.
- **D-06:** VS Code UI-only fields such as `presentation`, `internalConsoleOptions`, and `serverReadyAction` should be ignored silently.
- **D-07:** Unresolved variables should fail before launch with structured diagnostics rather than being passed literally or replaced with empty strings.
- **D-08:** Platform override support should include `osx`, `windows`, and `linux`, plus `mac` as a compatibility alias for `osx`.

### Workspace Discovery and CLI Shape
- **D-09:** `--workspace <path>` should control both `.vscode/launch.json` discovery and substitution roots such as `${workspaceFolder}` and `${workspaceFolderBasename}`.
- **D-10:** Add `--list-configs` so agents can enumerate both `configurations[]` and `compounds[]` without launching. Output should include each entry's kind; configuration entries should include useful type/request metadata, and compound entries should include member names.
- **D-11:** Keep `--config <name>` as the main selector for both configurations and compounds. Do not add a required separate `--compound` selector unless research/planning finds a strong ambiguity reason.

### Diagnostics and Unsupported Features
- **D-12:** `preLaunchTask` and `postDebugTask` should be ignored silently for this phase. This is an intentional divergence from the current `ROADMAP.md` text, which says to surface a structured diagnostic and bail. Planning must reconcile that conflict explicitly rather than treating it as accidental.
- **D-13:** Unsupported variables such as `${input:...}` and `${command:...}` are delegated to research/planning. The resulting behavior should stay consistent with D-07 and existing structured CLI error contracts.
- **D-14:** Exact error payload shapes for broken compounds, missing configs, unresolved variables, and adapter startup failures are delegated to planning, but they should remain agent-parseable and consistent with dap-cli's existing JSON envelope and `CliError` diagnostics.
- **D-15:** Whether compound member references are fully preflighted before launch is delegated to planning. The chosen behavior must preserve D-04's clean compound startup semantics.

### Verification Target
- **D-16:** Verification must include both deterministic in-repo fixture coverage and hand-driven real VS Code compound UAT.
- **D-17:** The real VS Code capstone succeeds only when `npx dap-cli launch --config "VS Code" --workspace /Users/roblou/code/vscode` brings up the renderer, main process, extension host, shared process, and agent host as one compound group, and a breakpoint in `chatWidget.ts` pauses the renderer after a Playwright-driven chat action.
- **D-18:** Real VS Code prerequisites are documented hard prerequisites, not auto-setup work for this phase. If `/Users/roblou/code/vscode` is not built or the required user data/profile state is missing, UAT should record that as an unmet prerequisite rather than silently skipping.
- **D-19:** The in-repo fixture coverage should prove both launch.json resolution and compound orchestration: variable substitution, platform merge, passthrough fields, compound group metadata, and `stopAll` cleanup behavior.

### The Agent's Discretion
- Resolve `--config` name collisions between a configuration and compound by researching VS Code behavior or choosing an ambiguity-safe rule.
- Define exact behavior and error codes for unsupported `${input:...}` and `${command:...}` variables.
- Define structured diagnostic payload details for missing configs, unresolved variables, broken compound members, and partial-start cleanup.
- Choose whether compound member references are validated entirely before launch or guarded through another implementation that still satisfies clean startup semantics.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `loadVSCodeLaunchConfig` in `src/config/launchConfig.ts` already parses JSONC `.vscode/launch.json`, enforces size/schema bounds, and returns named configurations; it needs compounds, workspace path input, variables, and platform overlay support.
- `resolveLaunchConfig` already models precedence as named config plus JSON plus flags. Preserve the Phase 3 precedence decision: flags > JSON > named config/defaults.
- `mapJsDebugFlags` and `mapDebugpyFlags` are the current lossy allowlists. Phase 05.2 should invert this shape toward passthrough/denylist so fields like `userDataDir`, `webRoot`, `cleanUp`, `pauseForSourceMap`, `browserLaunchLocation`, and `cascadeTerminateToConfigurations` survive.
- `SessionManager` and `SessionStore` already persist session records and can be extended for compound metadata, but exact optional-property handling and zod schemas need care.
- `ControllerServer.terminateRuntime`, `sessions.close`, and `sessions.cleanup --purge` already implement honest teardown and orphan PID reporting. Compound teardown should reuse that path.

### Established Patterns
- Core DAP behavior stays language-neutral; launch/config compatibility belongs in config/CLI/controller/session layers, not protocol internals.
- Adapter-specific config should remain adapter-native where possible, with dap-cli flags as convenience overrides.
- CLI commands emit one structured JSON envelope and use stable `CliError`/`usageError`/`sessionError` codes for handled failures.
- Child sessions from js-debug are hidden by default and not directly targetable. Compound member sessions are different: they should be user/agent targetable through derived names.
- Duplicate live top-level session names are rejected; derived compound member names must avoid violating that active-name collision rule.

### Integration Points
- Add `--workspace` and `--list-configs` in `src/cli/commands/dapCore.ts` without disturbing existing `launch`/`attach` JSON/flag behavior.
- Extend controller request/response types only as needed to support compound start results, group metadata, and list/status projection.
- Extend session persistence in a migration-tolerant way so existing sessions without compound fields continue to load.
- Tests should cover config resolution independently from adapter startup, then cover compound orchestration with fake/in-repo fixtures, then hand-driven real VS Code UAT.

</code_context>

<specifics>
## Specific Ideas

- The real VS Code `VS Code` compound includes `Launch VS Code Internal`, `Attach to Main Process`, `Attach to Extension Host`, `Attach to Shared Process`, and `Attach to Agent Host Process`.
- The real VS Code config uses fields dap-cli currently drops, including `userDataDir`, `webRoot`, `cleanUp`, `killBehavior`, `browserLaunchLocation`, `cascadeTerminateToConfigurations`, `pauseForSourceMap`, platform `osx` runtime executable, `${workspaceFolder}`, and `${userHome}`.
- The capstone should build from `docs/VSCODE-CHAT-SMOKE.md`: set a breakpoint in `src/vs/workbench/contrib/chat/browser/widget/chatWidget.ts`, use Playwright CLI to submit chat input, and observe the renderer pause through dap-cli.
- The current roadmap says task fields should be structured errors, but the user explicitly chose to ignore `preLaunchTask`/`postDebugTask` silently so the motivating VS Code compound can launch without implementing `tasks.json`.

</specifics>
