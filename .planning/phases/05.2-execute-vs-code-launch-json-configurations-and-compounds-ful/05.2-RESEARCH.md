# Phase 05.2 Research: VS Code launch.json fidelity and compounds

**Status:** Complete
**Date:** 2026-05-05

## Research Summary

Phase 05.2 needs standard in-repo implementation work, not a new external dependency. The repository already depends on `jsonc-parser`, which is the right parser for VS Code `launch.json` files because the motivating `/Users/roblou/code/vscode/.vscode/launch.json` uses JSONC/trailing commas. Existing dap-cli launch support is intentionally narrow: `loadVSCodeLaunchConfig` only returns `configurations[]`, `resolveNamedConfig` only searches `process.cwd()`, and `mapJsDebugFlags` / `mapDebugpyFlags` drop adapter-native fields through allowlists.

The implementation should keep the Phase 3 adapter-native configuration decision: dap-cli should resolve launch.json and CLI precedence, then pass adapter-native fields through to `js-debug` and `debugpy` except for small known-bad denylist entries. No protocol-core changes are needed.

## Behavioral Decisions for Delegated Areas

- Name collision between a configuration and a compound: fail as `launch_config_ambiguous` with `data: { name, matches: [{ kind, name }] }`. This is the safest agent-facing rule and keeps `--config` simple per D-11.
- Unsupported variables `${input:...}` and `${command:...}`: fail before launch as `unsupported_launch_variable`, with the variable token and JSON path in diagnostics/data. This is consistent with D-07 and avoids hidden prompts or VS Code extension command execution.
- Generic unresolved variables: fail before launch as `unresolved_launch_variable`, with the token and JSON path. Empty `${env:NAME}` values resolve to `process.env.NAME` when present and fail when absent.
- Compound member references: preflight every member name before starting adapters. This directly satisfies D-04 clean startup and produces deterministic `compound_member_not_found` diagnostics without partial adapter side effects.
