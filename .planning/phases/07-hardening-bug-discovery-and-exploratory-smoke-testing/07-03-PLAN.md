  <action>
Based on Task 1 investigation findings, add TypeScript/source-map diagnostic helpers:

**If the root cause is missing outFiles/sourceMaps in launch configs:**
- In `src/config/launchConfig.ts` or `src/adapters/builtins/jsDebug.ts`, create a helper `injectJsDebugSourceMapDefaults(config, workspaceFolder)` that:
  - If `config.type` is `'pwa-node'` or `'pwa-chrome'` AND `config.outFiles` is undefined AND the workspace has a `tsconfig.json`, inject a default `outFiles: ['${workspaceFolder}/**/*.js']` with a warning log that the default was applied.
  - If `config.sourceMaps` is undefined, set it to `true` by default for js-debug.
  - Apply this helper in the launch config resolution flow (Phase 5.2's `applyLaunchConfigOverrides` or similar).

**If the root cause is js-debug not reporting source-map failures clearly:**
- In `src/controller/diagnostics.ts`, add a `breakpointBindingGuidance()` helper that returns structured diagnostics when breakpoints remain unverified after a timeout:
  - Check if the session's launch config has `sourceMaps: false` → diagnostic: "Source maps are disabled. Set sourceMaps: true in launch.json."
  - Check if `outFiles` is missing → diagnostic: "TypeScript breakpoints may require outFiles in launch.json. Add: \"outFiles\": [\"${workspaceFolder}/**/*.js\"]"
  - Generic fallback: "Check tsconfig.json outDir, js-debug trace log, and ensure compiled JS includes source maps."

**If the root cause is that Phase 5.2's `mapJsDebugFlags` or config passthrough drops required fields:**
- Verify that `outFiles`, `sourceMaps`, `sourceMapPathOverrides`, `resolveSourceMapLocations` are NOT in any denylist/whitelist that would drop them.
- If they are being dropped, remove them from the denylist so they pass through to js-debug.

Do NOT implement a full source-map validator in this task — focus on catching the most common missing-config cases and surfacing actionable diagnostics. Full validation would require inspecting compiled JS files, which is out of scope.
  </action>
