# Phase 7 Hardening Matrix

## Purpose

Drive dap-cli as a published CLI, not only through Vitest harnesses. This matrix is the execution checklist for discovering bugs. Each row should finish with `result: pass`, `result: issue`, `result: blocked`, `result: skipped`, or `result: duplicate` and an evidence pointer into `07-UAT.md`.

## Severity Rubric

| Severity | Meaning |
|----------|---------|
| blocker | Prevents broad hardening from continuing or breaks a core launch/inspect/cleanup workflow. |
| major | A supported published workflow gives wrong output, misses required diagnostics, fails to stop/inspect/cleanup, or is unreliable without a workaround. |
| minor | Workflow succeeds but output, recovery guidance, ergonomics, or edge handling is confusing or incomplete. |
| cosmetic | Human-readable output, docs wording, alignment, or presentation issue that does not affect automation. |

## Filing Rules

- For `result: issue`, add a UAT gap immediately with `truth`, `status: failed`, `reason`, `severity`, `test`, `artifacts`, `missing`, and reproduction commands.
- For `result: duplicate`, point to the existing gap ID or section.
- For `result: blocked`, record the prerequisite and whether the scenario should be retried in a second discovery pass.
- Do not fix during this pass unless a blocker prevents unrelated discovery. If that happens, record the blocker first.

## Execution Notes

- Prefer `node dist/index.js` after `npm run build` for transcript fidelity.
- Use bounded commands and scenario-local cleanup. Avoid leaving Chrome, debugpy, node, or controller processes alive.
- Redact secrets if any environment output is captured.
- External repositories are untrusted input. Clone only into ignored scratch space, inspect scripts before running setup/build/run commands, do not run `sudo` or credentialed/cloud/deploy commands, and mark candidates blocked when setup is unsafe or too heavy.
