<objective>
Fix GAP-07-01: step-out and other DAP request failures from the adapter should preserve the actual error category (dap/adapter) instead of falling back to `controller_unavailable` with misleading "Run dap-cli start" diagnostics.

Purpose: Agents receive actionable diagnostics that reflect the actual failure reason (unsupported operation, invalid thread state, adapter limitation) instead of controller availability hints when the controller is running.

Output: Correct error category mapping, preserved adapter failure context, and regression test coverage for step-control adapter failures.
</objective>

  <action>
Inspect `src/controller/server.ts` `routeDapRequest` method to understand how adapter DAP request failures are caught and returned. The issue is likely that when the adapter returns a DAP error response (e.g., `{success: false, message: "Unable to step out"}`), the controller either:
1. Does not set an explicit error category in the IPC response, causing `src/controller/client.ts` to fall back to `controllerUnavailable()` in the catch-all branch, OR
2. Returns a generic failure without preserving the adapter's error details.

Fix by:
- In `routeDapRequest` (server.ts): when catching adapter request failures, create a `dapError()` or `adapterError()` with the adapter's message, the DAP command name, and adapter context (pid, stderr tail, log path) so the client receives a structured non-controller-category failure.
- In `createControllerClient` request method (client.ts): verify the error category mapping logic correctly handles `category: 'dap'` and `category: 'adapter'` from the IPC response, and only falls back to `controllerUnavailable()` when the response truly lacks a recognized category.
- Prefer `dapError()` for DAP protocol-level failures (adapter returned DAP error response) and `adapterError()` for adapter process/transport failures. For step-control failures like "Unable to step out", use `dapError()` because the adapter successfully communicated a DAP-level operation failure.

Do NOT change the thread_not_paused early-return logic added in Plan 05-20 (gap H-7) — that is a separate controller-side gate that runs before forwarding to the adapter. This fix targets the case where the request IS forwarded to the adapter and the adapter returns a failure.
  </action>
  <acceptance_criteria>

    - `grep -A10 "if (!response.ok)" src/controller/client.ts | grep -q "toCliErrorCategory"` (client maps category from IPC response)
    - `npm run build` succeeds
