<objective>
Stop forcing agents to know debugpy's "evaluate is an expression-only" rule (analysis2.md §Python). Detect statement-shaped Python on `evaluate` against a debugpy session and (default) auto-wrap with `exec("…")`; (fallback) when detection misses and the adapter returns a SyntaxError, upgrade the error envelope to `evaluate_requires_exec` naming the exact recipe to retry.

Per D-16 from CONTEXT.md: "A by default with `--no-auto-exec` to opt out, plus B as the catch-when-detection-misses safety net".

Purpose: Closes PYEVAL-01. Eliminates a documented agent-trap where multi-statement Python (`import …`, assignments, multi-line) returns raw `SyntaxError` instead of evaluating.

Output: One pure heuristic module, controller wiring, structured error upgrade, full unit + integration test coverage.
</objective>

  <name>Task 1: Pure Python statement heuristic</name>
  <files>src/controller/pythonExpressionDetector.ts, tests/controller/pythonExpressionDetector.test.ts</files>
  <behavior>
    Two pure exports:

    `looksLikePythonStatement(source: string): boolean` returns `true` iff `source`, after stripping leading/trailing whitespace, matches ANY of:
      - First non-whitespace token is one of these keywords (followed by space, `(`, `:`, or end of string): `import`, `from`, `def`, `class`, `if`, `elif`, `else`, `for`, `while`, `with`, `try`, `except`, `finally`, `raise`, `return`, `pass`, `break`, `continue`, `global`, `nonlocal`, `del`, `assert`, `yield`, `async`, `await` (NOTE: `await EXPR` is sometimes an expression at top level in Python ≥ 3.8 REPL; treat as statement-shape conservatively).
      - Contains a `;` outside of any string literal or `#` comment.
      - Contains a newline (`\n`) outside of any string literal.
      - Contains a top-level `=` that is NOT `==`, `!=`, `<=`, `>=`, `:=` (walrus), and NOT inside `()`, `[]`, `{}`, or a string literal — this catches plain assignment like `x = 1`. Top-level keyword args like `f(x=1)` are excluded by the bracket-depth check.

    Returns `false` for pure expressions: arithmetic, function calls (incl. kwargs), lambda, dict/list/set comprehensions, ternary, walrus, attribute access, indexing.

    `wrapForExec(source: string): string` returns `'exec(' + JSON.stringify(source) + ')'` so the adapter receives a single Python expression that triggers the statement when evaluated. (Use `JSON.stringify` because Python string-literal escaping is a strict superset of JSON's for `\n`, `"`, `\\`, control chars.)

    Tests:
      - Statement positives (one test per category): `import os`, `from x import y`, `def f(): pass`, `x = 1`, `if x:\n  y = 2`, `import x; y = 1`, `try:\n  pass\nexcept:\n  pass`, `del x`, `for i in range(3): print(i)`.
      - Expression negatives: `1 + 1`, `f(x=1, y=2)`, `[i for i in range(3)]`, `lambda x: x + 1`, `(x := 5)`, `a if b else c`, `obj.attr.method(arg)`, `dict[key]`, `'a' == 'b'`, `not x`, empty string, `   ` (whitespace only — return false).
      - `wrapForExec` round-trip: contains the original source verbatim inside a single `exec("...")` call; embedded newlines / quotes / backslashes survive a JSON.parse on the inner string.
  </behavior>
  <action>
    RED → GREEN → REFACTOR. Test file first; module file second; iterate until all cases pass. Implementation hint: a single linear scan tracking bracket depth + string state (handles `'`, `"`, `'''`, `"""`, escape backslashes) is enough — no full Python parser needed. Keep the module side-effect-free; no logging, no imports beyond the standard library / no project utils unless a JSON-string helper already exists (none does — use `JSON.stringify` directly).

    Per project convention (Rob's preferences: prefer ServicesAccessor / IInstantiationService etc. — N/A here, this is a pure module with no DI surface).

    Do NOT add any awareness of the controller, adapter, or DAP protocol in this module. It must remain a string-in / boolean-or-string-out helper so it can be unit-tested without any mocks.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Controller IPC → DAP adapter | Caller's `evaluate.expression` arg is mutated before being forwarded to debugpy. The controller becomes the source of truth for the wrapped form, not the caller. |
| Adapter error → controller envelope | Adapter SyntaxError text is matched against a regex to upgrade the error envelope. Adapter could in principle craft an error message that triggers the upgrade incorrectly. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-16-01 | Tampering | `maybePythonEvaluateRewrite` mutates caller args | mitigate | Rewrite is opt-out (caller can pass `context: 'no-auto-wrap'`). Negative test pins the opt-out path. Original expression is preserved on the error path so `data.exec_form` reflects the caller's input, not the wrapped form. |
| T-16-02 | Information Disclosure | `data.exec_form` echoes the caller's expression | accept | The expression is already controller-known (it was just submitted) and the envelope returns to the same caller. No cross-tenant exposure (controller is single-user). |
| T-16-03 | Tampering (heuristic mis-classification) | `looksLikePythonStatement` returning false for a real statement OR true for a real expression | mitigate | A. Rich positive/negative test matrix in Task 1 pins both directions. B. Mis-classification's worst case is the existing pre-phase behavior (raw SyntaxError) — but the Task 2 fallback turns that into the structured `evaluate_requires_exec` envelope, so the user still gets the recipe even if the heuristic missed. |
| T-16-04 | Spoofing (error-message match) | Adapter-supplied error message triggering `evaluate_requires_exec` upgrade incorrectly | accept | Match is gated on `adapterId === 'debugpy'` AND `command === 'evaluate'` AND `originalExpression !== undefined` (i.e. only when we actually saw an evaluate request). Worst case: a debugpy adapter genuinely returning "invalid syntax" for some non-statement reason gets the slightly-misleading recipe. The recipe is still safe to follow (wrapping a genuine SyntaxError-ing expression in `exec(...)` just produces the same SyntaxError inside `exec`, no escalation). |

</threat_model>
