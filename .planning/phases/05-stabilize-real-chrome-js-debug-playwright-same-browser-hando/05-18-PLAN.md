overwhelmed by js-debug `loadedSource` spam (93/100 in a single hello-world,
70 events dropped before the user can poll). Critical events — `stopped`,

plan, a hand-driven user MUST be able to run `events --name <name>` after a
stop-on-entry launch and see the `stopped` event without it being drowned by
loadedSource — both in Sequence A (Node) and Sequence B (Chrome).

Output: Two-ring DapEventCache (priority-segregated, configurable capacities)
+ CLI `--include` / `--exclude` filters + honest `truncatedToCapacity` +
`warnings: ['limit_exceeded_capacity: ...']`.
</objective>

    - Backwards-compatible: `new DapEventCache(N)` (positive integer) still works — treats N as highPriorityCapacity; lowPriorityCapacity defaults to `Math.max(10, Math.ceil(N / 4))`. Existing tests must not change.
    - `append()` routes by event name into the right ring. Each ring tracks its own droppedBeforeCursor.
    - `recent({ afterCursor?, limit? })` returns events from BOTH rings merged by cursor in ascending order, then filtered by `afterCursor`, then sliced by `limit` (last-N). Snapshot's `droppedBeforeCursor` is the MIN of the two rings' droppedBeforeCursor (representing the earliest cursor that's been evicted from at least one ring).

    - Tests: (a) flooding 1000 loadedSource events does NOT evict a single stopped event; (b) stopped/thread/output/terminated/breakpoint/startDebugging are HIGH priority by default; (c) merged recent() returns events in cursor order regardless of which ring they came from; (d) backwards-compat constructor `new DapEventCache(50)` still works and routes 'loadedSource' into a smaller low ring; (e) custom `lowPriorityEventNames` opt overrides the default set.
