<objective>
Close UAT gap 14 (blocker — controller dies on bad fake-adapter script).

Purpose: A single bad client request currently kills the daemon for every session. Two root causes:
  (a) Fake adapter doesn't validate that the chosen script matches the requested DAP mode; when no response is sent for the unexpected request, the controller hangs.
  (b) `DapLifecycleController.start` has no timeout on initialize / launch / configurationDone; a non-responding adapter blocks the controller event loop indefinitely until the IPC client times out, by which point the session future has been left dangling.

Output: Lifecycle handshake bounded by hard timeout; fake adapter emits a structured failure on first script ↔ mode mismatch; new regression test asserts a bad fake-script launch returns a structured error in <5s and the controller still answers `sessions` afterward.
</objective>

<interfaces>
From `src/protocol/lifecycle.ts`:
```typescript
export type DapLifecycleStartOptions =
  | { mode: 'launch'; initializeArgs?: unknown; launchArgs?: unknown; beforeConfigurationDone?: () => Promise<void> }
  | { mode: 'attach'; initializeArgs?: unknown; attachArgs?: unknown; beforeConfigurationDone?: () => Promise<void> };
export class DapLifecycleController {
  public constructor(private readonly client: DapLifecycleClient);
  public async start(options: DapLifecycleStartOptions): Promise<DapLifecycleStartResult>;
}
```

The fake adapter (`runFakeAdapterScript`) responds to each parsed request by popping the next `expectRequest` step. If the popped step's command does not match (e.g. script expects `attach`, request is `launch`), it currently writes a response with `success: false`. **However**, the bug surfaces with attach-mode scripts like `attach-stopped` whose first `expectRequest` is `attach`; when the client sends `launch`, the fake adapter does write a failure response, but the controller's lifecycle code never calls `request('launch')` until *after* `request('initialize')` resolves — and the `attach-stopped` script's first step *is* `initialize`, so initialize succeeds, then `launch` is sent against a script whose next step is `sendEvent: initialized` (not an expectRequest), and the request sits unreplied forever. The script-level check must therefore validate **at script construction time** that the script matches the lifecycle mode.
</interfaces>
