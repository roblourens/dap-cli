<objective>
Lay the protocol-level and session-model groundwork that the controller will need
to bring up js-debug child sessions. Today `DapClient.handleAdapterRequest` rejects
every adapter reverse request except `runInTerminal`, which causes the pwa-chrome
adapter's `startDebugging` requests (one per Chromium target it discovers) to be
dropped. With no child session ever opened to the dapDebugServer, the parent
pwa-chrome session never owns a real DAP thread and breakpoints can never bind.

This plan does NOT yet implement child session bring-up — that is plan 05-04.
This plan only:
- Generalises DapClient reverse-request handling so callers can subscribe.
- Extends the session model with optional parent/child linkage.
- Adds SessionManager registration helpers for child sessions.

Purpose: Unblock UAT gaps 1+2 (test 3 and test 4) by giving the controller a
seam to plug js-debug parent/child multiplexing into.

Output: Updated protocol + session model + tests; nothing in `src/controller/`
changes yet.
</objective>

<root_cause_pin>
From the 2026-05-03 debug session on `pwa-chrome-attach-launch-bugs`:

The pwa-chrome adapter (vscode-js-debug `dapDebugServer.js`) implements a
parent/child multiplexing model. After the parent pwa-chrome session attaches
or launches, the adapter discovers each Chromium target and issues a DAP
**reverse request** with `command: "startDebugging"` carrying a
`__pendingTargetId` argument. The DAP client is expected to open a *new*
DAP connection back to the same adapter and run a fresh
`initialize` / `attach` (or `launch`) / `configurationDone` lifecycle as a
*child* session. The parent session never owns a real browser thread; the
children do.

Today, `DapClient.handleAdapterRequest` rejects every command except
`runInTerminal` with `Unsupported adapter request: ${command}`, so:
- pwa-chrome ATTACH: child sessions are never opened → `threads` returns empty.
- pwa-chrome LAUNCH: setBreakpoints reaches the parent (which has no target)
  → js-debug reports the breakpoint as unbound.

This plan opens the seam. Plan 05-04 wires the actual child bring-up.
</root_cause_pin>

  <files>src/protocol/dapClient.ts, tests/protocol/dapClient.test.ts</files>
  <behavior>
    - Test 1 (existing behavior preserved): An adapter-issued runInTerminal request still spawns a child process and returns success when no onReverseRequest handler is registered.
    - Test 2 (new dispatch): When an onReverseRequest handler is registered, an adapter-issued startDebugging request is delivered to the handler verbatim (command + arguments + seq), and the handler's resolved value (`{ success, body?, message? }`) is written back to the adapter as a DAP response with the same request_seq.
    - Test 3 (handler rejection): If the registered handler resolves `{ success: false, message: 'no child support' }`, the adapter receives a failure response with that message.
    - Test 4 (no handler, unknown command): With no onReverseRequest handler, a startDebugging request still receives `success: false` with `Unsupported adapter request: startDebugging` (today's behavior; do NOT silently accept).
    - Test 5 (handler errors): If the handler throws or rejects, the failure surfaces back to the adapter as `success: false` with the error message; the DapClient does not crash.
  </behavior>
  <action>
    Refactor `DapClient.handleAdapterRequest` so it:
      1. First gives a registered `onReverseRequest` handler a chance to handle the request (any command including `runInTerminal`).
      2. Falls back to the existing built-in `runInTerminal` handler ONLY when no handler is registered or the handler explicitly returns `undefined` (i.e. "not handled").
      3. Falls back to the current "Unsupported adapter request: ${command}" failure response otherwise.

    Add a public method:
      ```typescript
      public onReverseRequest(handler: (request: { command: string; arguments: unknown; seq: number; }) =>
        Promise<{ success: boolean; body?: unknown; message?: string } | undefined> | undefined): () => void
      ```
    Returns a disposer. Only one handler at a time (later subscription replaces earlier — document this).

    Wire the handler call inside `handleAdapterRequest` defensively: catch synchronous and asynchronous errors and translate them to `writeAdapterResponse(request, false, undefined, err.message)`. Do NOT let handler errors propagate into the parser loop.

    Preserve `runInTerminal` as the default fallback so existing fakeAdapter tests continue to pass without registering a handler.

    Per D-01 (debug session root cause): this is the seam plan 05-04 will use to dispatch `startDebugging` to the controller.
  </action>
