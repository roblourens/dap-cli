<objective>
Wire the seam introduced in plan 05-03. When a parent js-debug session
(pwa-chrome / pwa-node / etc.) sends a `startDebugging` reverse request,
the controller must open a brand-new DAP transport to the *same* adapter
endpoint, run a fresh DAP lifecycle as a child session, and register the
child against the parent.

Once children exist, inspection requests (`threads`, `stack`, `scopes`,
`variables`, `setBreakpoints` against parent-owned sources) must route to
or aggregate across the children — the parent pwa-chrome session itself
never owns a real browser thread.

This closes the controller-side root cause behind UAT gaps 1 and 2.

Purpose: Make pwa-chrome attach + launch actually expose threads and bind
breakpoints inside the Playwright-owned Chromium target.

Output: Updated `src/controller/server.ts` (and supporting helpers); new
controller + integration test coverage proving child sessions appear and
threads become non-empty.
</objective>

<root_cause_pin>
js-debug's pwa-chrome adapter discovers each Chromium target after
attach/launch and issues a DAP reverse request:

```jsonc
{
  "type": "request",
  "command": "startDebugging",
  "arguments": {
    "request": "attach",      // or "launch"
    "configuration": { "__pendingTargetId": "<adapter-internal-id>", ... }
  }
}
```

The expected client behavior is to open a NEW DAP connection to the same
adapter endpoint (the dapDebugServer) and run a fresh
`initialize` + `attach|launch` (echoing the supplied `configuration`)
+ `configurationDone` lifecycle. That child session is the one that owns
the actual browser thread.
</root_cause_pin>

- `createInitializeArgs(adapterId)` (line 465) — use for child initialize.
- `createBeforeConfigurationDoneHook` (line 553) — keep as-is for parent; do NOT replicate for children.
- `parseDapStartParams` / `extractDapCliStartConfig` — used during parent start; the child reuses the parent's adapter endpoint.

From src/adapters/builtins/jsDebug.ts: the pwa-chrome adapter exposes a
single endpoint that accepts multiple DAP connections (the standard
dapDebugServer model). Reuse the parent's adapter runtime to produce a
new transport — do NOT spawn a new dapDebugServer process.

  <name>Task 1: Bring up child sessions on startDebugging reverse request</name>
  <files>src/controller/server.ts, tests/controller/sessionManager.test.ts</files>
  <behavior>
    - Test 1 (parent-only adapters unaffected): Adapters that never send `startDebugging` (the existing fakeAdapter, debugpy, etc.) continue to behave as today; no child sessions are created and `listChildren(parent.id)` returns `[]`.
    - Test 2 (child created on startDebugging): When a fake parent DapClient delivers a `startDebugging` reverse request with `arguments: { request: 'attach', configuration: { __pendingTargetId: 'tgt-1' } }`, the controller:
        a. Opens a new DAP transport to the parent's adapter runtime.
        b. Sends DAP `initialize` (using `createInitializeArgs(parent.adapterId)`).
        c. Sends DAP `attach` with `arguments` equal to the supplied `configuration` (verbatim, including `__pendingTargetId`).
        d. Sends DAP `configurationDone`.
        e. Calls `SessionManager.registerChild({ parent_session_id: parent.id, name: `${parent.name}#tgt-1`, ... })`.
        f. Resolves the reverse request with `{ success: true }` BEFORE waiting for the child's `configurationDone` response (the parent must not deadlock waiting on the client). The child lifecycle continues in the background; failures during initialize/attach/configurationDone surface as a `terminated` child SessionRecord plus a controller diagnostic event, NOT as a thrown error in the parent's reverse-request flow.
    - Test 3 (launch path): Same as Test 2 but with `arguments: { request: 'launch', configuration: {...} }` — the child sends `launch` instead of `attach`.
    - Test 4 (multiple targets): Two consecutive `startDebugging` requests with different `__pendingTargetId` values create two distinct child SessionRecords, both linked to the same parent.
    - Test 5 (failure surfaces): If the child's `attach` request fails, the child SessionRecord ends up in a terminated/failed lifecycle state; the parent stays running; `listChildren(parent.id)` still includes the failed child for observability.
  </behavior>
  <action>
    1. After `SessionManager.create()` succeeds for a session whose adapter is a js-debug variant (pwa-*), wire `parent.client.onReverseRequest(handler)` where `handler` does the following for `command === 'startDebugging'`:

        a. Acquire a fresh DAP transport from the SAME adapter runtime as the parent. The pwa-chrome dapDebugServer accepts multiple connections on the same socket endpoint — reuse the connection-creation path the parent used (look in `src/adapters/builtins/jsDebug.ts` for the existing transport factory; if needed, factor a small helper rather than duplicating launch logic).

        b. Construct a new `DapClient` over that transport.

        c. Run `initialize(createInitializeArgs(parent.adapter.id))` → `attach`/`launch` (echoing the supplied `configuration` verbatim) → `configurationDone`. Do NOT register a `before-configurationDone` hook on the child; the parent already owns the initial-breakpoint contract and the controller will forward setBreakpoints from the parent (Task 2).

        d. `SessionManager.registerChild({ parent_session_id: parent.id, name: `${parent.name}#${childIndex}`, lifecycle: 'running', ownedAdapter: parent.ownedAdapter, ... })`. Store the child's DapClient in the same runtime map the parent uses (so `threads`/`stack`/etc. can find it).

        e. Resolve the handler's promise with `{ success: true }` as soon as `attach`/`launch` has been *sent* (not awaited). Continue `configurationDone` and any post-init flow asynchronously. Catch errors and update the child SessionRecord lifecycle to `failed` / `terminated`; emit a controller diagnostic event so users see the failure via `events`.

        f. For commands other than `startDebugging`, return `undefined` so DapClient's built-in `runInTerminal` fallback still runs.

    2. When the parent SessionManager.close() runs, the child closures from plan 05-03 already cascade. Ensure the child DapClient is also closed (its transport ends).

    3. Add the five behaviors above to `tests/controller/sessionManager.test.ts` using a fakeAdapter that emits a synthetic `startDebugging` reverse request after attach. (Do NOT depend on real js-debug here — that is Task 3.)
  </action>

    - Test 4 (setBreakpoints fan-out): `dap.setBreakpoints` against the parent forwards the same arguments to every child as well. The aggregated response is `{ breakpoints: [...] }` with one entry per requested location, marked `verified: true` if ANY child verified it (record the scheme in the SUMMARY).     - Test 5 (events forwarded): `stopped`, `continued`, `thread`, `output`, `breakpoint`, `terminated` events from any child are mirrored into the parent session's event cache (with the child id annotated on the event payload) so the existing `events` polling command shows them when targeting the parent.
  </behavior>
  <action>
    1. Identify the existing request handlers in `src/controller/server.ts` for `dap.threads`, `dap.stack`, `dap.scopes`, `dap.variables`, `dap.setBreakpoints`, and the events polling path. For each, branch on `SessionManager.listChildren(parent.id).length > 0`:

    2. Pick a thread-id encoding that is reversible and unambiguous. Two reasonable options:
