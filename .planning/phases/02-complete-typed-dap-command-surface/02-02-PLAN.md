<objective>
Preserve the raw DAP escape hatch while adding capability reporting and handled unsupported-request diagnostics.

Purpose: Agents need complete protocol access through DAP-04 and clear machine-readable adapter capability behavior through DAP-05 before ergonomic aliases are layered on top.
Output: `dap.capabilities` controller/CLI support, stored initialize capabilities per runtime, and structured unsupported failures that retain Phase 1 JSON/error/session contracts.
</objective>

- Truth: D-04 is satisfied because `request <command> --json '{}'` remains a top-level command and still calls controller method `dap.request`.
- Truth: D-06 is satisfied because raw request and capability commands use the existing stdout JSON envelope, CliError categories, session targeting, and controller IPC client pattern.
- Truth: D-07 is satisfied because unsupported capabilities return handled JSON failures instead of thrown internal errors or raw adapter messages.
- Truth: D-08 is satisfied because `capabilities` returns machine-readable adapter capabilities and unsupported failures include request command, session ID, and adapter context.
- Truth: D-10 is satisfied because fake-adapter tests cover raw passthrough, capability reporting, and unsupported capability behavior.
- Artifact: src/controller/server.ts stores runtime capabilities and preflights gated requests.
- Key link: src/cli/commands/dapCore.ts calls `dap.request` and `dap.capabilities` through the controller client.
</must_haves>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CLI JSON -> controller IPC | User-provided request args and session target cross from CLI into daemon. |
| Controller -> adapter | DAP requests cross from trusted controller state to external adapter process. |
| Adapter capabilities -> CLI JSON | Adapter-declared support is surfaced to agents and used for preflight. |

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|

| T-02-02-02 | Information Disclosure | capability reporting | accept | Capabilities are non-secret adapter feature metadata; response is scoped to resolved explicit/active local session only. |
| T-02-02-03 | Repudiation | unsupported request failures | mitigate | Include request command, session ID, and adapter diagnostics in handled JSON failures so agents can attribute the failure. |
| T-02-02-04 | Elevation of Privilege | session targeting | mitigate | Reuse existing resolveRuntime explicit/active session semantics and do not add bypass routes around `dap.request`. |
</threat_model>
