<objective>
Build the source-of-truth machinery for the Phase 2 typed DAP command surface.

Purpose: DAP-03 and TEST-02 require every official DAP request to be discoverable as generated metadata, with deterministic diffs when the official protocol changes.
Output: A generator script, a committed generated registry artifact, a package script to regenerate it, and an architecture gate that keeps generated metadata separate from handwritten command behavior.
</objective>

<must_haves>
- Truth: D-01 is satisfied because official DAP protocol metadata is the request inventory source of truth, not a handwritten full command list.
- Truth: D-02 is satisfied because src/generated/dapCommandRegistry.ts is deterministic, committed, typed metadata for command, CLI, validation, routing, request type, and capability gate information.
- Truth: D-09 is satisfied because inventory tests can compare generated commands against the selected official DAP schema and fail on missing requests.
- Artifact: src/generator/dapCommandRegistryGenerator.ts fetches and parses the official schema.
- Artifact: src/generated/dapCommandRegistry.ts exports the generated metadata consumed by later plans.
- Key link: package.json `generate:dap-commands` regenerates the committed artifact and `git diff --exit-code src/generated/dapCommandRegistry.ts` verifies determinism.
</must_haves>

    Create src/generator/dapCommandRegistryGenerator.ts. Use async Node filesystem APIs and fetch the official DAP schema URL. Parse schema definitions whose names end in Request and extract command strings, request type names, request direction (`clientToAdapter` for the `Requests` title section and `adapterToClient` for the `Reverse Requests` title section), capability gate metadata where explicit supports* capability fields exist in the schema or installed @vscode/debugprotocol declarations, and argument validation metadata. The validation metadata must include `argsRequired`, required top-level argument property names, and direct JSON-schema property validators for string, integer, number, boolean, array, and object fields when the request arguments `$ref` resolves to an object definition. Emit stable sorted TypeScript to src/generated/dapCommandRegistry.ts with exported types DapGeneratedCommandMetadata, DapGeneratedArgumentValidation, and DapGeneratedCommandRegistry, a readonly dapGeneratedCommands array, and a getDapGeneratedCommand(command: string) helper. Add package.json script "generate:dap-commands" that runs the generator through the existing TypeScript/Node toolchain without adding runtime dependencies. This implements D-01 and D-02.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Official schema URL -> generator | Network metadata enters the build-time generator. |
| Generator -> committed TypeScript | Parsed schema data becomes executable project source. |
| Generated registry -> CLI/controller | Metadata later influences user-visible command routing. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01-01 | Tampering | src/generator/dapCommandRegistryGenerator.ts | mitigate | Fetch only the official DAP schema URL per D-01, sort output deterministically, and require `git diff --exit-code src/generated/dapCommandRegistry.ts` after regeneration. |
| T-02-01-02 | Denial of Service | generator schema parsing | mitigate | Validate parsed request metadata as unknown input and fail generation with a clear error if command/type fields are absent or duplicated. |
| T-02-01-03 | Elevation of Privilege | src/generated/dapCommandRegistry.ts | mitigate | Keep generated output metadata-only with architecture tests forbidding imports from CLI, controller, adapter, session, or protocol runtime modules. |
</threat_model>
