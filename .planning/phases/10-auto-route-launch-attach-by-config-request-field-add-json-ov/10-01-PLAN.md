<objective>
Stop the silent verb/config mismatch documented in `analysis.md`. When `--config <name>` is used, the resolved launch.json `request:` field becomes the source of truth: if it disagrees with the CLI verb (`dap-cli launch` vs `dap-cli attach`), dap-cli auto-routes to the matching DAP request and emits a structured warning. No `--config` → unchanged behavior.

Purpose: Today `dap-cli launch --config "Attach to Agent Host Process"` against an attach-shaped config (`request:'attach'`) silently sends a DAP `launch` request. js-debug then spawns a bare `node` helper, reports it as the debuggee, and the real attach target is never touched. Symptoms cascade (bogus `process.pid`, empty `require.cache`, breakpoints stay `Unbound`). The `--config` name is unambiguous about the intended request — we should honor it.
Output: A small targeted edit to `startDap` that reads `namedEntry.configuration.request`, rebinds the effective mode, and emits a warning; unit + integration coverage of all four (verb × config.request) cases; docs explaining the rule.
</objective>

    // Phase 10 plan 01: when --config is used, the resolved launch.json
    // `request:` field is the source of truth. Mirrors createCompoundStartMember.
    const effectiveMode: 'launch' | 'attach' =
      namedConfig?.request === 'attach' ? 'attach'
      : namedConfig?.request === 'launch' ? 'launch'
      : mode;
    const autoRouted = effectiveMode !== mode;
    // ... existing adapter/flags/config build ...
    const config = {
      ...await mapConfigForAdapter(adapterId, resolveLaunchConfig({ namedConfig: { ...adapterDefaults, ...namedConfig }, jsonConfig, flags: adapterFlags }), workspace),
      request: effectiveMode,
    };
    // ... existing descriptor build ...
    const client = await createControllerClient({ dapCliHome: process.env.DAP_CLI_HOME, timeoutMs: startControllerRequestTimeoutMs });
    try {
      const response = await client.request('dap.start', {
        mode: effectiveMode,
        name: options.name ?? 'default',
        use: options.use !== false,
        descriptor,
        config,

      const payload = autoRouted

            autoRouted: { code: 'auto_routed_to', from: mode, to: effectiveMode, configName: options.config },

        : response;
      output.success(payload, { command: effectiveMode });
    } finally {
      await client.close();
    }

## Trust Boundaries

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-01-01 | Tampering | `namedConfig.request` | accept | The `request:` field is already part of the workspace-trusted launch.json (Phase 5.2 schema validation). Auto-routing it is no more privileged than honoring `type:` or `program:`. No new attack surface. |
| T-10-01-02 | Spoofing | success payload `autoRouted` field | accept | Field is local-only (not signed); attackers with stdout access can already inject anything. JSON consumers should treat the field as advisory, same as `warnings`. |
| T-10-01-03 | Information Disclosure | `autoRouted.configName` echoes user-supplied `--config` argument | mitigate | Echoing the user's own argument back to them is not disclosure. No mitigation needed. |
</threat_model>
