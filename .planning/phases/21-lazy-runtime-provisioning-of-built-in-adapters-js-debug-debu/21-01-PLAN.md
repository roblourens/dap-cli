<objective>
Land the cross-cutting provisioning scaffold that every per-adapter provisioner will use: lockfile, atomic staged install, HTTP download (with undici ProxyAgent + structured error classification), in-process tar.gz and zip extract, consent prompt, sentinel-file consent markers, and the program-level `--yes` / `DAP_CLI_ASSUME_YES` plumbing. Purpose: This plan does NOT trigger any real download. It exists so 21-02 (per-adapter provisioners) and 21-03 (`setup-adapters` subcommand) can compose pre-built, tested primitives instead of inventing them inline. Landing the scaffolding first keeps each downstream plan small and focused.

Output: New `src/adapters/provision/` module with five primitives, new `src/cli/confirm.ts`, `--yes` wiring through the commander program, async `AdapterRegistry.resolve()`, and unit tests for each primitive.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CLI argv → `--yes` flag | User-controlled input that elevates a confirmation prompt to auto-yes. |
| Env var → `DAP_CLI_ASSUME_YES` | Process env that pre-consents provisioning without an interactive prompt. |
| File system → lock sentinel + staging dir | Concurrent dap-cli processes coordinate via filesystem state. |
| Network → archive download | HTTPS fetch with optional proxy; classification of failures determines what the user sees. |
| Archive → extracted tree | Untrusted archive entries could escape `dest` via `..` paths or symlinks. |
