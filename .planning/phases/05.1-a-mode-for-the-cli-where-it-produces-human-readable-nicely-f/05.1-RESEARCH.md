## User Constraints (from CONTEXT.md)

### Locked Decisions
## Implementation Decisions

### Output Mode Selection
- **D-01:** JSON remains the default output mode for dap-cli commands. Existing agent workflows and tests that parse stdout JSON envelopes must continue to work without new flags.
- **D-02:** Human-readable output is selected with a global `--human` flag rather than `--format human|json`, `--pretty`, or changing defaults.
- **D-03:** dap-cli should also support an environment-variable default for human output so a human can configure their shell to prefer readable output without passing `--human` every time.
- **D-04:** Command-line selection must take precedence over the environment default. Planning should preserve a way for explicit machine-output needs to get JSON even when the environment prefers human output.
- **D-05:** The existing command-level `--json` options are payload inputs, especially for raw DAP requests and launch configuration, not output-format switches. Do not create an output-mode shape that confuses those meanings.

### the agent's Discretion
- Choose the exact environment variable name and validation behavior, as long as the behavior is documented and invalid or absent configuration cannot silently break the default JSON contract.
- Choose the exact internal formatter architecture and whether to implement curated renderers first with a generic fallback, as long as the user-facing mode decisions above hold.
- Choose the exact human-readable layout for individual commands, including tables, labeled sections, diagnostics formatting, and color policy.
- Choose the test breakdown, but include coverage that proves default JSON behavior is preserved and `--human`/environment selection changes output only when requested.

## Summary

Phase 05.1 should be planned as a presentation-layer refactor around the existing JSON envelope boundary, not as per-command string construction. `src/cli/output.ts` already centralizes success/failure envelope shapes, `src/cli/main.ts` centralizes handled failure routing, and the command modules call `writeJsonSuccess` with structured data. [VERIFIED: src/cli/output.ts, src/cli/main.ts, src/cli/commands/*.ts]

The recommended implementation is to replace direct `writeJsonSuccess` / `writeJsonFailure` calls with an `OutputWriter` abstraction that can render either JSON envelopes or human text from the same structured success/failure inputs. JSON must remain the default, `--human` should be a root Commander option, and `--no-human` should be added as the explicit machine-output override when the environment default prefers human output. [VERIFIED: 05.1-CONTEXT.md; VERIFIED: commander probe]

Do not reuse `--json` for output mode. `launch`, `attach`, raw `request`, and generated `dap <request>` commands already use `--json <json>` as a payload/config input flag. [VERIFIED: src/cli/commands/dapCore.ts, src/cli/commands/dapGenerated.ts]

**Primary recommendation:** Add a root `--human` / `--no-human` output-mode switch, manually parse `DAP_CLI_HUMAN`, and route all success/failure rendering through a shared output writer with curated renderers plus a generic `util.inspect` fallback. [VERIFIED: 05.1-CONTEXT.md; ASSUMED]

### Pattern 1: Mode-Aware Output Writer

**What:** Keep commands returning structured data and centralize the final write in a writer with `success` and `failure` methods. [VERIFIED: src/cli/commands/*.ts]

**When to use:** Use for every command that currently calls `writeJsonSuccess` and for every handled failure in `main`. [VERIFIED: src/cli/main.ts, src/cli/commands/*.ts]

**Example:**

```typescript
// Source: repo pattern from src/cli/output.ts and src/cli/main.ts
export type OutputMode = 'json' | 'human';

export interface OutputWriter {
  success<T>(data: T, meta: JsonMetaInput): void;
  failure(error: CliError, meta: JsonMetaInput): void;
}

export function createOutputWriter(options: {
  stream: JsonWritable;
  resolveMode: () => OutputMode;
}): OutputWriter {
  return {
    success(data, meta) {
      if (options.resolveMode() === 'human') {
        options.stream.write(toHumanSuccess(data, meta));
        return;
      }
      writeJsonSuccess(data, meta, options.stream);
    },
    failure(error, meta) {
      if (options.resolveMode() === 'human') {
        options.stream.write(toHumanFailure(error, meta));
        return;
      }
      writeJsonFailure(error, meta, options.stream);
    },
  };
}
```

### Pattern 2: Explicit CLI Precedence Over Environment

**What:** Resolve output mode as explicit CLI flag first, then environment default, then JSON default. [VERIFIED: 05.1-CONTEXT.md]

**When to use:** Use in both success and handled failure paths so `dap-cli status --human` and `dap-cli status --no-human` behave consistently. [VERIFIED: src/cli/main.ts]

**Example:**

```typescript
// Source: Commander option behavior verified from /tj/commander.js docs and local probe.
export function resolveOutputMode(input: {
  cliHuman: boolean | undefined;
  env: NodeJS.ProcessEnv;
}): OutputMode {
  if (input.cliHuman === true) {
    return 'human';
  }
  if (input.cliHuman === false) {
    return 'json';
  }
  return parseHumanEnv(input.env.DAP_CLI_HUMAN) === true ? 'human' : 'json';
}
```

### Pattern 3: Curated Renderers With Generic Fallback

**What:** Provide specific renderers for high-value commands (`sessions`, `status`, `events`, `breakpoints set`, `threads`, `stack`, `scopes`, `variables`, `evaluate`, `cleanup`, `close`) and use a generic fallback for generated/raw DAP responses. [VERIFIED: src/cli/commands/sessions.ts, src/cli/commands/dapAliases.ts, src/cli/commands/dapGenerated.ts]

**When to use:** Use curated output when the command/result shape is stable and frequently read by humans; use fallback for the generated DAP command surface where result bodies are adapter-specific. [ASSUMED]

**Example:**

```typescript
// Source: data shapes verified from src/sessions/session.ts and src/controller/server.ts.
export function renderSessions(data: unknown): string | undefined {
  if (!Array.isArray(data)) {
    return undefined;
  }
  const rows = data.filter(isRecord).map(session => ({
    id: String(session.id ?? ''),
    name: String(session.name ?? ''),
    status: String(session.status ?? ''),
    adapter: String(session.adapter ?? ''),
  }));
  return `${formatTable(rows)}\n`;
}
```

### Anti-Patterns to Avoid

- **Parsing JSON back out of stdout to render human text:** The writer should receive structured data before serialization, because `writeJsonSuccess` already serializes to a newline-terminated JSON string. [VERIFIED: src/cli/output.ts]
- **Changing default output based on TTY detection:** The locked decision says JSON remains default unless the caller opts into human output. [VERIFIED: 05.1-CONTEXT.md]
- **Making `--json` an output flag:** Existing commands use `--json <json>` for launch/attach config and DAP request arguments. [VERIFIED: src/cli/commands/dapCore.ts, src/cli/commands/dapGenerated.ts]
- **Rendering errors on stderr in human mode:** Existing handled failures write stdout output and leave stderr empty; changing streams would surprise automation and tests. [VERIFIED: tests/cli/jsonOutput.test.ts, tests/cli/errorContracts.test.ts]
- **Formatting by command module side effects:** Command modules should keep requesting structured data and let the writer render it, preserving the `cli/` boundary. [VERIFIED: copilot-instructions.md, src/cli/commands/*.ts]

## Common Pitfalls

### Pitfall 1: `--json` Name Collision

**What goes wrong:** A planner treats `--json` as output mode or adds `--format json`, confusing it with existing payload flags. [VERIFIED: src/cli/commands/dapCore.ts, src/cli/commands/dapGenerated.ts]

**Why it happens:** Many CLIs use `--json` for output, but dap-cli already uses it for raw launch/attach/request input. [VERIFIED: src/cli/commands/dapCore.ts]

**How to avoid:** Use only `--human` / `--no-human` for output selection and document that existing `--json` flags remain payload inputs. [VERIFIED: 05.1-CONTEXT.md]

**Warning signs:** Tests involving `request stackTrace --json '{"threadId":1}'` or generated `dap continue --json '{"threadId":1}'` start failing or rendering the wrong mode. [VERIFIED: tests/cli/jsonOutput.test.ts, tests/cli/dapGeneratedCommands.test.ts]

### Pitfall 2: Breaking the One-Envelope Default

**What goes wrong:** Default mode emits multiple lines, pretty JSON, stderr text, or non-envelope output. [VERIFIED: tests/cli/jsonOutput.test.ts]

**Why it happens:** Human rendering gets wired into existing writers without an explicit mode gate. [ASSUMED]

**How to avoid:** Keep `writeJsonSuccess`, `writeJsonFailure`, and `toJsonString` behavior unchanged; add tests proving default stdout remains exactly one newline-terminated JSON envelope. [VERIFIED: src/cli/output.ts, tests/cli/jsonOutput.test.ts]

**Warning signs:** `tests/helpers/runCli.ts` throws `CLI stdout contained X JSON lines` or JSON parse failures in tests that did not request human mode. [VERIFIED: tests/helpers/runCli.ts]

### Pitfall 3: Invalid Environment Defaults Surprise Agents

**What goes wrong:** An inherited env var turns agent commands into human text or makes output mode ambiguous. [ASSUMED]

**Why it happens:** Environment defaults are global shell state and Commander boolean env parsing is presence-based. [VERIFIED: node_modules/commander/lib/command.js]

**How to avoid:** Use `DAP_CLI_HUMAN` with explicit accepted values, let CLI flags override it, and render invalid-env failures as JSON unless `--human` was explicitly selected. [ASSUMED]

**Warning signs:** `DAP_CLI_HUMAN=0 dap-cli status` produces human output, or `DAP_CLI_HUMAN=maybe dap-cli status` silently changes behavior. [VERIFIED: commander env source; ASSUMED]

### Pitfall 4: Snapshot Churn From Timestamps, PIDs, and Paths

**What goes wrong:** Human-output snapshots become flaky because they include timestamps, process IDs, temp paths, controller endpoints, log paths, or adapter PIDs. [VERIFIED: src/cli/output.ts, src/controller/server.ts, src/sessions/session.ts]

**Why it happens:** Current JSON meta includes timestamps and controller/session data includes dynamic values. [VERIFIED: src/cli/output.ts, src/controller/server.ts]

**How to avoid:** Assert substrings and stable layout sections for dynamic commands; use inline snapshots only for pure renderer functions with fixed fixture data. [CITED: Context7 /vitest-dev/vitest; ASSUMED]

**Warning signs:** Tests need repeated snapshot updates after unrelated runs. [ASSUMED]

### Pitfall 5: Terminal Control Characters in Adapter/Data Output

**What goes wrong:** Human output displays adapter stderr, evaluated strings, source content, or DAP output containing ANSI/control characters that confuse terminals or snapshots. [VERIFIED: src/cli/errors.ts, src/cli/output.ts; ASSUMED]

**Why it happens:** dap-cli can surface adapter stderr tails, source content, variables, and evaluate results from external debug adapters. [VERIFIED: src/cli/errors.ts, src/cli/commands/dapAliases.ts]

**How to avoid:** Prefer plain text without color in v1, escape or visibly replace control characters in human renderers, and keep raw details available in JSON mode. [ASSUMED]

**Warning signs:** Human-mode tests pass locally but fail in CI due to escape codes or terminal-width differences. [ASSUMED]

### Environment Parser

```typescript
// Source: project env pattern in tests/helpers/runCli.ts; parser behavior is a recommendation.
export type HumanEnvValue = true | false | undefined;

export function parseHumanEnv(value: string | undefined): HumanEnvValue {
  if (value === undefined || value.trim() === '') {
    return undefined;
  }
  const normalized = value.trim().toLowerCase();
  if (['1', 'true', 'yes', 'on', 'human'].includes(normalized)) {
    return true;
  }
  if (['0', 'false', 'no', 'off', 'json'].includes(normalized)) {
    return false;
  }
  throw usageError('Invalid DAP_CLI_HUMAN value.', {
    code: 'invalid_output_mode_env',
    diagnostics: ['Use DAP_CLI_HUMAN=1 for human output or DAP_CLI_HUMAN=0 for JSON output.'],
  });
}
```

### Human Failure Renderer

```typescript
// Source: JsonErrorPayload fields from src/cli/output.ts.
export function toHumanFailure(error: CliError, meta: JsonMetaInput): string {
  const lines = [
    `Error: ${error.message}`,
    `Code: ${error.code}`,
    `Category: ${error.category}`,
    `Exit code: ${error.exitCode}`,
  ];
  if (error.diagnostics.length > 0) {
    lines.push('', 'Diagnostics:', ...error.diagnostics.map(diagnostic => `- ${sanitizeForTerminal(diagnostic)}`));
  }
  if (error.adapter?.logPath !== undefined) {
    lines.push('', `Adapter log: ${error.adapter.logPath}`);
  }
  return `${lines.join('\n')}\n`;
}
```

## Open Questions (RESOLVED)

1. **Exact env variable value policy**
   - What we know: An env default is required and CLI selection must take precedence. [VERIFIED: 05.1-CONTEXT.md]
  - Resolution: Use `DAP_CLI_HUMAN` as the environment default and fail with JSON `invalid_output_mode_env` when it contains an invalid value and no explicit CLI flag overrides it. `--human` and `--no-human` take precedence over the environment. [RESOLVED]

2. **Minimum curated command coverage**
   - What we know: Aliases and sessions/status/events are strong candidates because humans read them often. [VERIFIED: 05.1-CONTEXT.md, src/cli/commands/*.ts]
  - Resolution: Phase 05.1 should include curated human renderers for common/session/debugging commands and a generic sanitized fallback for generated/raw DAP responses. Bespoke formatting for every generated DAP command is out of scope. [RESOLVED]

3. **Color policy**
   - What we know: No color dependency exists today and tests use memory streams without TTY metadata. [VERIFIED: package.json, tests/helpers/runCli.ts]
  - Resolution: Ship deterministic plain text first. Color, TTY detection, and new color dependencies are out of scope for Phase 05.1. [RESOLVED]
