# Phase 05.1: A mode for the CLI where it produces human-readable nicely formatted output instead of JSON. - Context

**Gathered:** 2026-05-05
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 05.1 adds an opt-in human-readable output mode for dap-cli so humans can run the same debugging commands and see nicely formatted text instead of raw JSON envelopes. This phase must preserve dap-cli's existing agent-facing machine contract: JSON output remains the default, exit codes remain stable, and existing automation that parses one stdout JSON envelope must keep working unless the caller explicitly opts into human output.

This phase is about presentation mode selection and formatted command results. It does not add a TUI/watch mode, event streaming, graphical debugger UI, or new debugger capabilities beyond presenting existing command data differently.

</domain>

<decisions>
## Implementation Decisions

### Output Mode Selection
- **D-01:** JSON remains the default output mode for dap-cli commands. Existing agent workflows and tests that parse stdout JSON envelopes must continue to work without new flags.
- **D-02:** Human-readable output is selected with a global `--human` flag rather than `--format human|json`, `--pretty`, or changing defaults.
- **D-03:** dap-cli should also support an environment-variable default for human output so a human can configure their shell to prefer readable output without passing `--human` every time.
- **D-04:** Command-line selection must take precedence over the environment default. Planning should preserve a way for explicit machine-output needs to get JSON even when the environment prefers human output.
- **D-05:** The existing command-level `--json` options are payload inputs, especially for raw DAP requests and launch configuration, not output-format switches. Do not create an output-mode shape that confuses those meanings.

### the agent's Discretion
- Choose the exact environment variable name and validation behavior, as long as the behavior is documented and invalid or absent configuration cannot silently break the default JSON contract.
- Choose the exact internal formatter architecture and whether to implement curated renderers first with a generic fallback, as long as the user-facing mode decisions above hold.
- Choose the exact human-readable layout for individual commands, including tables, labeled sections, diagnostics formatting, and color policy.
- Choose the test breakdown, but include coverage that proves default JSON behavior is preserved and `--human`/environment selection changes output only when requested.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `src/cli/output.ts` centralizes JSON success/failure writing and metadata creation. A human-output layer should reuse the same success/failure data rather than making command modules produce unrelated strings.
- `src/cli/main.ts` is the central place where handled failures are converted into output; human-readable failures need to pass through this same error taxonomy.
- `src/cli/program.ts` is the likely home for a global `--human` option and for passing output-mode configuration into registered commands.
- Command modules already accept a `JsonWritable` stdout and call `writeJsonSuccess` from small controller wrappers; this gives a clear integration point for replacing only the final rendering path.
- `tests/helpers/runCli.ts` can keep the default JSON parser while gaining a separate helper or option for human-mode assertions.

### Established Patterns
- Default successful commands write a single newline-terminated JSON envelope to stdout.
- Handled failures write a single JSON envelope to stdout and leave stderr empty.
- Command metadata includes the command name and timestamp in JSON envelopes.
- Raw DAP and launch commands already use `--json` to mean input payload/config; output-mode naming must avoid colliding with that established option.
- Integration and CLI tests isolate `DAP_CLI_HOME` and assert stable exit codes and structured failures.

### Integration Points
- Output-mode resolution should occur before command actions render success output and before `main` renders handled failures.
- A global output writer abstraction can preserve existing command modules while selecting JSON or human rendering at the boundary.
- Docs and tests must make the default-vs-human distinction explicit so agent workflows continue to use JSON reliably.

</code_context>

<specifics>
## Specific Ideas

- `--human` should be the user-facing opt-in flag.
- An environment variable should be available for humans who want readable output by default in their shell.
- JSON should remain the default even in interactive terminals unless the caller opts into human mode through the flag or environment.
- The planner should treat command coverage and exact formatting as implementation discretion unless later product work adds more specific requirements.
