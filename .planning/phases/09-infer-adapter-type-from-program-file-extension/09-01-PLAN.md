<objective>
Make `--type` and `--adapter` optional on `dap-cli launch` and `dap-cli attach` by inferring the missing pieces from `--program` (and from each other) when unambiguous. Explicit flags always override.

Purpose: Today `dap-cli launch --program app.js` silently falls back to the `fake` adapter, and `--type python --program x.py` requires the user to also repeat `--adapter debugpy`. Both are friction the CLI can remove.
Output: A pure `programInference` module, refactored `dapCore` wiring, unit + integration coverage for every branch, and updated README/ADAPTER-SETUP docs.
</objective>

    1. `inferAdapterAndType(args)` where `args = { adapter?: string; type?: string; program?: string; customTypeMap?: Record<string,string> }` returns `{ adapterId: string; type?: string; inferred: { adapter: boolean; type: boolean } }` OR throws a `usageError` with the exact codes below.

    2. Resolution precedence (first matching branch wins):
       - **Both `adapter` and `type` given** → `{ adapterId: adapter, type, inferred: { adapter: false, type: false } }`. No validation that adapter and type "agree" — explicit wins.
       - **Only `adapter` given** → `{ adapterId: adapter, type: defaultTypeForAdapter(adapter, program), inferred: { adapter: false, type: true } }` where `defaultTypeForAdapter`:
         - `js-debug` + program ending `.html`/`.htm` → `'pwa-chrome'`
         - `js-debug` otherwise → `'pwa-node'`
         - `debugpy` → `'python'`
         - any other (custom) adapter → `undefined` (don't fabricate a type for unknown adapters)
       - **Only `type` given** → `{ adapterId: resolveAdapterIdFromType(type, customTypeMap), type, inferred: { adapter: true, type: false } }`. Re-throws `resolveAdapterIdFromType`'s existing `unknown_launch_type` error unchanged.
       - **Only `program` given** → look up extension in the table below. On match: `{ adapterId, type, inferred: { adapter: true, type: true } }`. On miss: throw `usageError('Cannot infer adapter from program extension <ext>. Pass --adapter or --type explicitly.', { code: 'adapter_inference_failed', data: { program, extension } })`.
       - **None given** → return `{ adapterId: 'fake', type: undefined, inferred: { adapter: false, type: false } }` to preserve the existing default. (Caller still constructs the fake descriptor as today.)

    3. Extension table (lower-cased ext, leading dot included):
       - `.py` → `{ adapterId: 'debugpy', type: 'python' }`
       - `.js`, `.mjs`, `.cjs` → `{ adapterId: 'js-debug', type: 'pwa-node' }`
       - `.ts`, `.mts`, `.cts` → `{ adapterId: 'js-debug', type: 'pwa-node' }`
       - `.html`, `.htm` → `{ adapterId: 'js-debug', type: 'pwa-chrome' }`
       - anything else → no match (throws as above).

    4. Extension extraction MUST use `path.extname(program).toLowerCase()`. Programs with no extension (`./run`, `python -m foo` style, etc.) trigger the same `adapter_inference_failed` error as unsupported extensions, with `extension: ''`.

    Unit tests (one per bullet, plus the negative cases):
      - both given returns both untouched, `inferred` both false
      - adapter-only: js-debug + `.html` → `pwa-chrome`; js-debug + `.js` → `pwa-node`; js-debug + no program → `pwa-node`; debugpy → `python`; custom `my-adapter` → `type: undefined`
      - type-only: `node` → js-debug; `python` → debugpy; unknown type re-throws `unknown_launch_type`
      - type-only respects `customTypeMap`: `{ fakeType: 'custom-fake' }` + `--type fakeType` → `custom-fake`
      - program-only: each extension in the table maps as documented; `.html` chooses `pwa-chrome`; `.foo` throws `adapter_inference_failed` with `data.extension === '.foo'`; `./run` (no ext) throws with `data.extension === ''`
      - none given → `{ adapterId: 'fake', type: undefined }`
      - case-insensitive: `App.JS` matches `.js`
  </behavior>

<threat_model>
## Trust Boundaries

| Boundary | Description |
| --- | --- |
| CLI user input (`--program`, `--type`, `--adapter`) → adapter selection + DAP launch config | A user-supplied program path is parsed for its extension and used to pick which adapter binary the controller spawns. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
| --- | --- | --- | --- | --- |
| T-09-01-01 | Tampering | `inferAdapterAndType` extension lookup | mitigate | Extension table is a hardcoded record; lookup is `path.extname(program).toLowerCase()` then a property read with `Object.hasOwn`-equivalent semantics. No dynamic `require`, no spawning a binary derived from the program path. The adapter id returned is then resolved by the existing `AdapterRegistry`, which already restricts adapter ids to its registered built-ins and config-declared customs. |
| T-09-01-02 | Elevation of Privilege | adapter-only branch defaulting `type` for custom adapters | mitigate | `defaultTypeForAdapter` returns `undefined` for any non-built-in adapter id, so a malicious or misconfigured custom adapter cannot trick dap-cli into picking a privileged DAP type on its behalf. |
| T-09-01-03 | Information Disclosure | `adapter_inference_failed` error data | accept | Error includes `program` (echoes the user-supplied path) and `extension`. The user supplied this path themselves; no new disclosure. |
| T-09-01-04 | Denial of Service | inference path on every `launch`/`attach` | accept | Inference is a single `path.extname` + property lookup; no I/O, no allocation beyond a small result object. |
</threat_model>
