  <action>
Update `src/controller/requests.ts` handleDapStart to properly support attach mode. Currently both launch and attach modes call `lifecycle.start(config)` - this needs to dispatch based on mode.

Changes to handleDapStart:
```typescript
// After DAP initialize and capabilities received:
if (params.mode === 'launch') {
  await lifecycle.start({ request: 'launch', ...config });
} else {
  await lifecycle.start({ request: 'attach', ...config });
}
```

The DAP protocol differentiates launch (start new process) from attach (connect to existing process) via the `request` field in the launch/attach request body.

Update `src/cli/commands/dapCore.ts` attach command to remove the Phase 1 restriction:
- Remove the check that only allows fake adapter
- Use adapter registry resolution (already added in Plan 01)
- Ensure attach-specific config is passed through correctly

Note: The actual attach behavior (what ports to connect to, what process IDs, etc.) is adapter-specific and comes from the launch/attach config. dap-cli just passes the config to the adapter via DAP.

Add basic validation: If adapter capabilities don't include `supportsAttachRequest`, log a warning but attempt attach anyway (adapter may still support it even if capability not advertised).

<task type="auto">
  <name>Task 2: Improve adapter process cleanup and error diagnostics</name>
  <files>src/adapters/processAdapter.ts</files>
  <action>
Enhance `src/adapters/processAdapter.ts` with better cleanup and diagnostics. Review the existing close() implementation and add:

**Improved cleanup:**
- Send SIGTERM before SIGKILL for graceful shutdown
- Wait briefly (100ms) for process to exit after SIGTERM before escalating to SIGKILL
- Close log file handles explicitly to avoid file descriptor leaks
- Clear any pending timers or event listeners

**Enhanced error diagnostics:**
- When adapter process crashes, include exit code, signal, and last 10 lines of stderr in error message
- When adapter fails to start (no response to initialize), include full stderr and log path in error
- Timeout detection: If adapter doesn't respond to DAP request within 10s, report timeout with adapter PID and log path

Example pattern:
```typescript
export async function close(metadata: ProcessAdapterMetadata): Promise<void> {
  const { pid } = metadata;
  
  try {
    // Try graceful shutdown first
    process.kill(pid, 'SIGTERM');
    
    // Wait briefly for process to exit
    await new Promise(resolve => setTimeout(resolve, 100));
    
    // Check if still running
    if (isProcessRunning(pid)) {
      process.kill(pid, 'SIGKILL');
    }
  } catch (err) {
    // Process already dead or doesn't exist - this is fine
  }
  
  // Close log handles (if open)
  // ...
}
```

Keep changes focused on cleanup and diagnostics - do not change the adapter spawn or transport logic.

  </verify>
